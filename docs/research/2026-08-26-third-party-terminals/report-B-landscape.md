# Landscape sweep: coding-agent runtimes vs. the comms push/poll/resume-driver contract

Seat: sonnet-scout-B. Read-only outside `/tmp/pr63-w/research`. Nothing under `~/code/comms`, `~/.claude`, `~/.codex` was written. No mailbox posts made.

## Premise check — FALSE, reported per brief instructions rather than delivered silently

The brief's premise: "among these runtimes, Claude Code, Codex CLI, and possibly Gemini CLI are the only ones that inject a tool-boundary hook's stdout into the model's next turn; every other one either has no tool-boundary hook or has one whose output goes to logs/UI only."

**This is false.** Reading primary sources (source code at cloned origin HEAD, or official docs) turned up context-injection mechanisms of some kind on **at least 8 of the 15 swept runtimes**, not 2-3:

- **Gemini CLI** — GROUNDED, unambiguous. `AfterTool` hook output's `additionalContext` is appended directly into the tool result's `llmContent` (`packages/core/src/core/coreToolHookTriggers.ts:216-233`), which is what the model reads next turn. Literal PostToolUse analog with JSON-stdin payload carrying `session_id`/`cwd`/`tool_name`/`tool_input` (`packages/core/src/hooks/types.ts:141-144`). The strongest inversion: code-verified, not a docs claim.
- **OpenCode** — GROUNDED, different mechanism. `tool.execute.after` is an in-process JS/TS plugin hook (not a subprocess+stdin-JSON hook); the `output` object is passed by reference and returned as the tool result (`packages/opencode/src/session/tools.ts:118-124`), so a plugin can mutate it before the model sees it. More capable than "push" in the comms sense, but a structurally different channel — exactly the inversion path the brief's own "cheapest measurement" hint anticipated.
- **Cline** — GROUNDED. `PostToolUse` → `afterTool`'s `contextModification` becomes `appendContext`, and the adapter code's own comment states: "The runtime injects appendContext into the conversation as a `<hook_context>` block" (`apps/vscode/src/sdk/hooks-adapter.ts:215-221`). Cline's hook JSON shape (`cancel`/`contextModification`/`errorMessage`) is its own, not Claude-shaped.
- **Crush** (charmbracelet) — GROUNDED via its own docs. Currently ships only `PreToolUse`, whose `context` field is documented as "Appended to what the model sees" (`docs/hooks/README.md`), and the doc states hooks are "Claude Code-compatible" in stdin shape. Pre- rather than post-boundary, and no PostToolUse yet ("plans to support the full gamut").
- **Hermes Agent** (NousResearch) — GROUNDED via its own docs. "Shell hooks" are literally the comms shape: subprocess, JSON on stdin, JSON parsed from stdout. `pre_tool_call`/`post_tool_call` are real tool-boundary events, and `pre_llm_call`'s `{"context": "..."}` return is appended to the user message once per turn before the tool loop.
- **Amp** (Sourcegraph) — GROUNDED via its own docs, but via a plugin API (`amp.on('tool.call', ...)`), not a shell hook. The `synthesize` action ("Provide a synthesized result without actually running the tool") is model-visible; whether `tool.result` (the AfterTool analog) can inject text is genuinely ambiguous in the fetched doc — flagged UNVERIFIED below, not claimed as a clean inversion.
- **Cursor CLI**, **GitHub Copilot CLI**, **Factory Droid CLI** — DOCS say push (`postToolUse` → `additionalContext`/`hookSpecificOutput.additionalContext` appended to what the model sees), matching the Claude Code shape closely. But this is exactly the trap `adapters/CONTRACT.md` warns about (a doc claim is not a measurement): Cursor has multiple live, unresolved community bug reports saying the documented injection does not reach the model in practice, and GitHub's own `copilot-cli` repo has an open, maintainer-unconfirmed issue (opened 2026-04-26) reporting the identical failure mode for Copilot CLI. Nobody here ran the actual probe against either. Recorded as "docs say push, unverified / disputed," not as a measured push.

What the premise got right: **Roo Code**, **Kilo Code**'s main VS Code extension, **Aider**, **Warp**, and (structurally) **Conductor**/**Zed's External Agents** genuinely have no tool-boundary hook of their own (Kilo Code has an open feature request, #5827, explicitly asking for something "similar to OpenCode" — an asserted absence, not silence). Those need poll or wraps-X, as the premise assumed.

**Cheapest re-check that would move this further:** run `adapters/probe/` (or its non-Claude-shaped-config equivalent) against Gemini CLI, Cline, and Crush headless, the same way it was run against grok and Codex. Everything above is source-read or docs-read, at the CONTRACT.md tier of "vendor docs do not settle this" for the three DISPUTED rows, and at the "code read, not yet measured on this machine" tier for the five GROUNDED-by-source rows. None of these eight has had `probe-verdict.sh` run against it.

- **Codex CLI**: read `codex-rs/config/src/hook_config.rs` and `codex-rs/config/src/hooks_tests.rs` at origin HEAD `5af6979986a2` (2026-08-27) directly, not the comms adapter's prose. `HooksFile` (the struct that deserializes `~/.codex/hooks.json`) has `#[serde(deny_unknown_fields)]` and a `hooks: HookEventsToml` field, and the test `hooks_file_deserializes_existing_json_shape` (`hooks_tests.rs:12-53`) feeds it exactly the WRAPPED shape `{"hooks": {"PreToolUse": [...]}}` and asserts it parses; a flat top-level shape has no code path that constructs a `HooksFile` from it. `additionalContextLimit` appears as a per-hook config field, consistent with `additionalContext` support. **Agrees** with `adapters/codex/README.md`'s claim (wrapped shape required, `--dangerously-bypass-hook-trust` needed headless). One general web search surfaced a third-party blog (agenticcontrolplane.com) claiming Codex reads a FLAT `hooks.json` with "no hooks wrapper" — that source disagrees with both the comms repo and this independent source-code read. It is not Codex's own docs, so it is discounted here as a lower-trust secondary source, not treated as a genuine disagreement to reconcile.

**No inversion on the positive controls.** Both agree with `adapters/CONTRACT.md`.

## What would have to be built, per runtime

- **Claude Code, Codex CLI**: nothing — already wired.
- **Gemini CLI**: a `.gemini/hooks/comms-heartbeat.sh` wired to `AfterTool`, running `bin/comms read` and emitting `hookSpecificOutput.additionalContext`; needs its own `install.sh` (schema differs from Claude's) and an actual probe run — this sweep read code, it did not measure.
- **OpenCode**: a `.opencode/plugins/comms.js` implementing `tool.execute.after`, shelling to `bin/comms read` via the plugin's Bun `$`, appending into `output`. New adapter category — in-process plugin, not hook-subprocess; doesn't fit the existing template cleanly.
- **Cline**: a hook script under `.clinerules/hooks` (or global dir) in Cline's own JSON shape, not Claude's — needs a shape-translation layer.
- **Roo Code, Kilo Code (main ext)**: pi-recipe poll brief via `execute_command`.
- **Kilo Code KiloClaw**: same as OpenCode (it is OpenCode).
- **Aider**: pi-recipe poll brief via `/run`, flagged unreliable; fallback is an external resume-driver-shaped loop re-invoking `aider --message` per turn.
- **Crush**: wire `swarm-heartbeat.sh` (or a thin envelope-compatible wrapper) as `PreToolUse` in `crush.json` — no `PostToolUse` exists yet.
- **Amp**: `amp.on('tool.call', ...)` with `synthesize` replaces rather than augments the call — probably the wrong shape; `tool.result`'s injection needs confirming before design.
- **Factory Droid CLI, GitHub Copilot CLI, Cursor CLI**: run `adapters/probe/`-equivalent headless before writing any adapter — docs claim push, live bug reports say at least two of three don't deliver.
- **Zed Agent (native)**: pi-recipe poll brief.
- **Zed External Agents / Terminal Threads, Conductor**: nothing new — wire whichever wrapped CLI's adapter; wrapping is transparent to delivery.
- **Warp**: pi-recipe poll brief, same "is this really agent-autonomous" caveat as Aider.
- **Hermes**: a `~/.hermes/config.yaml` shell hook on `pre_llm_call` running `bin/comms read`, returning `{"context": "..."}`. Separately, a gateway mirror (`adapters/discord/`-shaped, not push) to any of its ~20 supported chat platforms — a much bigger mirror surface than Discord alone.
- **Grok**: unchanged (poll); re-probe on newer grok remains the standing open item in its own README.

## Open questions this sweep could not settle

1. **Amp's `tool.result` (AfterTool) injection capability** — the plugin-api doc fetch was internally ambiguous. Needs a direct source read (closed) or a live probe.
2. **Whether Cursor's and Copilot CLI's `additionalContext` bugs are version-specific or universal** — neither bug report pins a CLI version.
3. **Whether Warp's and Aider's shell-command capability is genuinely agent-autonomous mid-turn** vs. requiring user approval — neither vendor's docs settle this; no live run was possible here.
4. **Zed's `crates/agent*` grep was not exhaustive** — a large Rust monorepo, grepped for literal strings rather than read line-by-line the way Gemini/Cline/OpenCode were. Weaker than those GROUNDED rows.

6. **Roo-Code's and Aider's `main` branch being genuinely stale (2026-05)** relative to today (2026-08-26) was confirmed real (checked `git remote show origin` for both, not a shallow-clone artifact), but the cause was not investigated — out of scope, flagged so it isn't mistaken for a broken clone.
